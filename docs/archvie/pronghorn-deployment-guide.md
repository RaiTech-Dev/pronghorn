## Part 1 — How Environment Variables Work in This App

Before touching anything, you need to understand this because it affects every other decision.

### Vite env vars are compile-time, not runtime

This app uses Vite as its build tool. Vite has a special convention: any variable prefixed with `VITE_` in your `.env` file gets **replaced at compile time** inside the JavaScript bundle. This means:

- `import.meta.env.VITE_SUPABASE_URL` in source code
- Gets replaced by Vite with the literal string value during `npm run build`
- The final JS file in `dist/` contains no variable reference — just the raw value baked in

**Consequence for Docker:** You cannot change `VITE_*` values at container runtime by setting environment variables. The values are already burned into the JS files. To change them, you must **rebuild the Docker image** with new build args. For a homelab this is fine — you build once with your values and redeploy when they change.

### The current client.ts does NOT use env vars at all

This is the critical bug. The Supabase client file hardcodes the original project's credentials directly in the source code. It does not call `import.meta.env` anywhere. The consequence: even if your `.env` file has correct values, the app ignores them and connects to Alberta's Supabase project — not yours.

This is the **first thing you fix**. Everything else depends on it.

### Change 3: OAuth Redirect URLs

**File:** `src/contexts/AuthContext.tsx`

**What's wrong:** Lines 104 and 115 hardcode `https://pronghorn.red/dashboard` as the OAuth redirect target. When a user completes Google or Azure login, Supabase redirects them to this URL. If this points to someone else's domain, your users get sent to Alberta's production app after login.

**Before (lines 100–119):**
```typescript
const signInWithGoogle = async () => {
  const { error } = await supabase.auth.signInWithOAuth({
    provider: 'google',
    options: {
      redirectTo: 'https://pronghorn.red/dashboard',
      skipBrowserRedirect: false,
    }
  });
  return { error };
};

const signInWithAzure = async () => {
  const { error } = await supabase.auth.signInWithOAuth({
    provider: 'azure',
    options: {
      redirectTo: 'https://pronghorn.red/dashboard',
      scopes: 'openid profile email',
      skipBrowserRedirect: false,
    }
  });
  return { error };
};
```

**After:**
```typescript
const signInWithGoogle = async () => {
  const { error } = await supabase.auth.signInWithOAuth({
    provider: 'google',
    options: {
      redirectTo: `${import.meta.env.VITE_APP_URL ?? window.location.origin}/dashboard`,
      skipBrowserRedirect: false,
    }
  });
  return { error };
};

const signInWithAzure = async () => {
  const { error } = await supabase.auth.signInWithOAuth({
    provider: 'azure',
    options: {
      redirectTo: `${import.meta.env.VITE_APP_URL ?? window.location.origin}/dashboard`,
      scopes: 'openid profile email',
      skipBrowserRedirect: false,
    }
  });
  return { error };
};
```

**Why the `window.location.origin` fallback:** This is safer than hardcoding. `window.location.origin` is the protocol + host + port of wherever the app is running (e.g., `http://192.168.1.100:8080`). It means OAuth redirect works correctly on any machine without needing to set a `VITE_APP_URL` env var — useful if you access the app from multiple IP addresses or hostnames on your LAN. If you have a fixed domain (e.g., `https://pronghorn.rai-tech.ca`), set `VITE_APP_URL` in your `.env` file and it will be used instead.

**Add `VITE_APP_URL` to your `.env` file (optional but recommended if you have a domain):**
```env
VITE_APP_URL=http://192.168.1.100:8080
```

**Validate:** In your browser's dev tools, run `window.location.origin` on the page where your app is running. That value should match what you see in the OAuth consent redirect_uri during a login attempt. You can observe the redirect_uri in the browser's network tab when Google's auth page loads.

### File 2: `Dockerfile`

**Location:** Repo root

**Purpose:** Two-stage build. Stage 1 uses Node.js to compile the React app into static files. Stage 2 copies those static files into a lean Nginx image. The result is a container that serves your compiled SPA.

**Why two stages:** The Node.js image (~1.1 GB) is only needed to run `npm run build`. The final image only needs Nginx (~40 MB) to serve static files. Two-stage builds discard the build tooling and keep the image small.

```dockerfile
# ── Stage 1: Build ──────────────────────────────────────────────────
FROM node:20-alpine AS builder

WORKDIR /app

# Install dependencies first (Docker layer cache — only reruns if package.json changes)
COPY package.json package-lock.json* bun.lockb* ./
RUN npm ci --frozen-lockfile

# Copy all source code
COPY . .

# Declare build arguments — these come from docker-compose.yml's args section
# They are passed as env vars to npm run build, which means Vite bakes them
# into the JS bundle at compile time
ARG VITE_SUPABASE_URL
ARG VITE_SUPABASE_PUBLISHABLE_KEY
ARG VITE_SUPABASE_PROJECT_ID
ARG VITE_ADMIN_KEY
ARG VITE_APP_URL

ENV VITE_SUPABASE_URL=$VITE_SUPABASE_URL
ENV VITE_SUPABASE_PUBLISHABLE_KEY=$VITE_SUPABASE_PUBLISHABLE_KEY
ENV VITE_SUPABASE_PROJECT_ID=$VITE_SUPABASE_PROJECT_ID
ENV VITE_ADMIN_KEY=$VITE_ADMIN_KEY
ENV VITE_APP_URL=$VITE_APP_URL

# Compile the SPA — output lands in dist/
RUN npm run build

# ── Stage 2: Serve ──────────────────────────────────────────────────
FROM nginx:1.27-alpine AS runner

# Remove the default Nginx welcome page config
RUN rm /etc/nginx/conf.d/default.conf

# Install your custom Nginx config
COPY nginx.conf /etc/nginx/conf.d/pronghorn.conf

# Copy the compiled SPA from the builder stage
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

**Validate:** After writing this file, run `docker build --no-cache -t pronghorn-test .` from the repo root (with your `.env.local` set as build args, or see the Docker Compose section). The build completes without errors and produces an image. Run `docker images | grep pronghorn-test` — you should see it listed with a size under 100 MB.

### File 3: `nginx.conf`

**Location:** Repo root

**Purpose:** Configures Nginx inside the container. The most critical line is the SPA fallback: `try_files $uri $uri/ /index.html`. Without this, navigating directly to any URL like `/dashboard` or `/project/123/canvas` returns a 404 because those paths don't exist as real files on disk — they only exist as React Router routes handled in JavaScript.

```nginx
server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    # Serve pre-compressed files when the browser supports them
    # Vite builds both .br (Brotli) and .gz (Gzip) versions of every asset
    gzip_static on;

    # Security headers — standard for any web app
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # Long cache for hashed assets — safe because Vite puts content hashes
    # in filenames (e.g., vendor-react-Abc123.js), so a changed file = new filename
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # Medium cache for icons and manifests
    location ~* \.(ico|png|svg|webmanifest)$ {
        expires 7d;
        add_header Cache-Control "public";
    }

    # SPA fallback — the most important rule
    # If a file exists at the requested path, serve it
    # Otherwise fall back to index.html and let React Router handle it
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Never cache index.html — it's the bootstrap for the entire app
    # The browser must check for a new version on every visit
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
        expires 0;
    }
}
```

**Why no `brotli_static on`:** The standard `nginx:1.27-alpine` image does not include the ngx_brotli module. Adding `brotli_static on` would cause Nginx to fail to start with an unknown directive error. `gzip_static on` IS included and works fine — the `.gz` files Vite produces will be served to browsers that support it (all modern browsers do).

**Validate:** After the container is running, open DevTools → Network → reload the page. Click on any `vendor-*.js` asset. In the response headers, look for `Content-Encoding: gzip`. If you see it, Nginx is serving compressed files correctly. Also navigate directly to `http://your-ip:8080/dashboard` in a new tab without logging in first — you should get the app (login redirect), not a 404.

### File 4: `docker-compose.yml`

**Location:** Repo root

**Purpose:** Defines the container stack, connects your `.env.local` values to the Docker build args, and maps the container port to your host.

```yaml
services:
  frontend:
    build:
      context: .
      dockerfile: Dockerfile
      # These args are passed to the Dockerfile's ARG declarations
      # Docker Compose reads them from your .env.local file automatically
      args:
        VITE_SUPABASE_URL: ${VITE_SUPABASE_URL}
        VITE_SUPABASE_PUBLISHABLE_KEY: ${VITE_SUPABASE_PUBLISHABLE_KEY}
        VITE_SUPABASE_PROJECT_ID: ${VITE_SUPABASE_PROJECT_ID}
        VITE_ADMIN_KEY: ${VITE_ADMIN_KEY}
        VITE_APP_URL: ${VITE_APP_URL}
    image: pronghorn-frontend:local
    container_name: pronghorn-frontend
    restart: unless-stopped
    ports:
      - "8080:80"   # host:container — access at http://YOUR_IP:8080
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://localhost/index.html || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 15s
```

**How Docker Compose reads `.env.local`:** By default, Docker Compose reads a file named `.env` in the same directory. To use `.env.local`, you pass `--env-file`:

```bash
docker compose --env-file .env.local up -d
docker compose --env-file .env.local build
```

Alternatively, rename your env file to `.env` and use `.gitignore` to keep it out of git. Either approach works.

**Validate:** After running `docker compose --env-file .env.local up -d`:
```bash
# Container is running
docker compose ps

# Health check is passing (should show "healthy" after ~30s)
docker inspect pronghorn-frontend --format='{{.State.Health.Status}}'

# Logs show no errors
docker compose logs frontend
```

## Part 4 — Supabase Project Setup (No Code)

These are configuration steps done entirely in the Supabase Dashboard — no source code changes required.

### Step 1: Create the Project

1. Go to **supabase.com** → New Project
2. Choose a region closest to your homelab (reduces latency for edge function → database round trips)
3. Set a database password — write it down, you'll need it for Phase 2 (self-hosted Postgres migration)
4. Wait ~2 minutes for provisioning

### Step 2: Run Migrations

All 15+ tables, enums, indexes, RLS policies, and RPC functions are defined in `supabase/migrations/`. You apply them with the Supabase CLI.

```bash
# Install CLI (if not already installed)
# Windows via npm:
npm install -g supabase

# Authenticate
supabase login

# Link CLI to your new project
supabase link --project-ref YOUR_PROJECT_ID

# Push all migrations in order
supabase db push
```

**Validate:** In Supabase Dashboard → Table Editor, you should see tables including: `projects`, `requirements`, `canvas_nodes`, `canvas_edges`, `audit_runs`, `build_sessions`, `artifacts`, `profiles`, `organizations`, `share_tokens`, `standards`, `build_books`.

### Step 3: Configure Auth Settings

In Supabase Dashboard → Authentication:

| Setting | Location | Value |
|---------|----------|-------|
| Site URL | Authentication → URL Configuration | `http://YOUR_IP:8080` |
| Redirect URLs | Authentication → URL Configuration | Add `http://YOUR_IP:8080/**` |
| Email confirmation | Authentication → Providers → Email | Your choice — disable for easier local testing |

**Why the wildcard in Redirect URLs:** The `/**` wildcard allows Supabase Auth to redirect to any path under your domain (e.g., `/dashboard`, `/auth`, `/project/123`). Without it, Supabase rejects the redirect for security.

**If you're using a domain instead of IP:** Set Site URL and Redirect URLs to your domain. OAuth redirects will fail if they don't match what you put here.

**Validate:** In the Supabase Dashboard, go to Authentication → URL Configuration. Confirm Site URL shows your IP/domain and that your IP/domain appears in the allowed redirect list.

### Step 4: Deploy Edge Functions


### Step 5: Set Edge Function Secrets

In Supabase Dashboard → Settings → Edge Functions → Manage Secrets, add the following:

#### Required — App Won't Work Without These

| Secret Name | Where to Get It | Notes |
|-------------|----------------|-------|
| `GEMINI_API_KEY` | Google AI Studio (aistudio.google.com) → API Keys | Primary LLM. Used by almost every AI feature. Enable "Generative Language API" in Google Cloud Console. |
| `ANTHROPIC_API_KEY` | console.anthropic.com → API Keys | Claude streaming chat. Get from Anthropic Console. |
| `GITHUB_PAT` | github.com → Settings → Developer Settings → Personal Access Tokens → Classic | Required for Repository and Build features. Scopes: `repo` (full access), `read:org` |

#### Optional — Specific Features

| Secret Name | Feature It Unlocks | Where to Get It |
|-------------|-------------------|----------------|
| `GROK_API_KEY` | xAI Grok as an alternative LLM | console.x.ai → API Keys |
| `RENDER_API_KEY` | Deploy tab — provision Render.com databases/services | render.com → Account Settings → API Keys |
| `RENDER_OWNER_ID` | Deploy tab (same feature as above) | render.com → Account Settings — your account ID |
| `RESEND_API_KEY` | Branded signup/password reset emails | resend.com → API Keys |

**About `RESEND_API_KEY`:** If you don't set this, the `send-auth-email` edge function (which handles signup and password reset) will fail. However, Supabase has its own built-in email system that handles auth emails by default. The edge function is only needed if you want custom branded emails. For a personal homelab instance, you can skip Resend and use Supabase's default email. **But** — the signup flow calls `send-auth-email` directly from `AuthContext.tsx` (line 51). If that function fails without Resend configured, signup will error. See the signup gate section below for how to handle this.

**About the signup gate:** The `validate-signup-code` edge function already handles your use case gracefully. Looking at the actual source (lines 16–20):
```typescript
const validCode = Deno.env.get("SIGNUP_CODE");

if (!validCode) {
  // If no code is configured, allow all signups
  return new Response(JSON.stringify({ valid: true }), ...);
}
```
If you do NOT set a `SIGNUP_CODE` secret in your project, the function returns `{ valid: true }` automatically — no code required. The signup modal will still appear (it's a frontend component), but whatever the user types will be accepted. **No code changes needed for this.**

**Validate:** In Supabase Dashboard → Settings → Edge Functions → Manage Secrets, confirm you can see your secret keys listed (values are hidden, only names visible).

## Part 5 — Build and Run

### Build the Docker image

```bash
docker compose --env-file .env.local build
```

What happens:
1. Docker reads `.env.local` for the build arg values
2. Node 20 Alpine installs npm dependencies
3. `npm run build` compiles the React app with your `VITE_*` values baked in
4. Nginx Alpine copies the built files
5. Final image is tagged `pronghorn-frontend:local`

First build takes 5–10 minutes (downloading Node + Nginx images, installing npm deps, compiling). Subsequent builds where only source code changed (not `package.json`) take ~2 minutes due to layer caching.

### Start the container

```bash
docker compose --env-file .env.local up -d
```

### Check it's running

```bash
# See container status
docker compose ps

# Watch logs in real time
docker compose logs -f frontend

# Check health check status
docker inspect pronghorn-frontend --format='{{.State.Health.Status}}'
```

### Stop and update

```bash
# Stop
docker compose down

# Rebuild after code changes
docker compose --env-file .env.local build --no-cache

# Start again
docker compose --env-file .env.local up -d
```

## Part 7 — Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| App loads but all API calls fail | `client.ts` still has hardcoded old project URL | Verify Change 1 was applied and rebuild the Docker image |
| "Invalid API key" errors in console | Build was done before `.env.local` had correct values | Rebuild with `--no-cache` after verifying `.env.local` |
| Direct URLs (like `/dashboard`) return 404 | `nginx.conf` missing or SPA fallback not configured | Verify `try_files $uri $uri/ /index.html;` is in your `nginx.conf` |
| After Google/Azure login, redirects to `pronghorn.red` | Change 3 (AuthContext.tsx) not applied or image not rebuilt | Apply the fix, rebuild, also check Supabase Auth redirect URL allowlist |
| Signup fails with edge function error | `send-auth-email` function missing Resend key | Either set `RESEND_API_KEY` or modify the signup flow to use Supabase's native auth |
| "Signup code invalid" even after submitting anything | `SIGNUP_CODE` secret is set in your Supabase project | Go to Supabase → Settings → Edge Functions → Manage Secrets → delete `SIGNUP_CODE` |
| Share links still show `pronghorn.red` | Changes 4–7 not applied, or image not rebuilt after changes | Apply all changes in Part 2, rebuild with `--no-cache` |
| Container starts but health check stays "unhealthy" | Nginx failing to start — likely bad nginx.conf syntax | Run `docker compose logs frontend` to see Nginx error |
| Old project ID appears in network tab | `client.ts` fix was applied but image wasn't rebuilt | Run `docker compose build --no-cache` |

## Part 8 — What Changes If You Switch to a Domain (HTTPS)

When you're ready to put this behind a real domain with TLS:

1. Add your domain to Supabase → Authentication → URL Configuration → Redirect URLs
2. Update `VITE_APP_URL` in `.env.local` to `https://yourdomain.com`
3. Rebuild the Docker image (new `VITE_APP_URL` value gets baked in)
4. Add your reverse proxy (Nginx, Traefik, Caddy) in front — this handles TLS termination
5. The Pronghorn Nginx container doesn't need any changes — it still listens on port 80, and your reverse proxy handles HTTPS → HTTP internally
